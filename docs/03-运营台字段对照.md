# 运营台字段对照：厂商面板 → 我们的库 → 画布位置

底稿是 `AMZ-Purchase-Assistant/docs/vendor-panel-analysis.md`（厂商面板 smallbee168.com 的字段级只读观察，
12,963 单规模）。那张「Amazon拍单」列表是他们 100% 的工作量所在，值得逐字段抄一遍再决定取舍。

对照的规则：**我们库里没有的字段，画布上不许出现**。反过来，画布上画了的，
`refdata/schema.sql` 里必须有落点。

---

## 1. 筛选区

厂商 9 个可见筛选 + 5 个接口存在但界面没有。我们的取舍：

| 厂商筛选 | 参数 | 我们 | 落到哪个字段 |
|---|---|---|---|
| 平台订单号（textarea，**批量，每行一个**） | `orderNo` | **要，并且扩了** | `tasks.upstream_order_no` / `tasks.amazon_order_no` —— 两种号混着粘，形如 `111-xxxxxxx-xxxxxxx` 的走 AMZ 号，其余走上游号 |
| AMZ订单号（单个） | `platformOrderNo` | 合并进上面那个 | 同上。运营手里的表两种号混排是常态，不该逼人先分好类 |
| 状态 | `status` | 要 | `tasks.status`（我们 7 个，他们 4 个） |
| 买家号 | `buyerAccount` | 要 | `buyer_envs.code` |
| 创建时间区间 | `createTimeStart/End` | 要 | `tasks.created_at` |
| 拍单时间区间 | `purchaseTimeStart/End` | 要 | `tasks.purchased_at` |
| 国家 | `country` | **首期不做** | `tasks.marketplace` 恒为 `US` |
| 店铺名称 | `storeName` | **不做** | 我们库里没有店铺概念，店铺留在上游 ERP |
| 备注 | `remark` | **不做** | 没有批次导入，也就没有批次备注 |
| 物流状态（多选） | `orderStatus` | 挪到物流轨迹页 | `logistics.shipments.status` |

画布上「创建时间 / 采购时间」做成了一个二选一的开关，而不是两组日期框：
同时按两个时间维度筛的场景不存在，而表格最后一列会跟着开关变——按哪个维度筛，就看哪个时间。

选「采购时间」时，没下过单的行整体消失。这不是 bug：按采购时间筛本来就是在问「哪些单已经买了」。

批量单号一旦生效就**盖过状态桶和时间范围**，并且横幅上报「匹配 3 / 4 · 1 个没找到」。
按号找单的人是来找特定几张单的，不是来做统计的；而没找到的那个号必须说出来——
厂商面板在这里是静默的，粘 100 个号回来 87 条，运营不会知道少了哪 13 个。

## 2. 列表列

厂商 9 列全部塞在一行里（店铺/买家/产品/订单/费用/物流/买家号/其他/操作），横向拖得很远。
我们把它拆成「表格只放决策需要的，详情放右侧抽屉」：

| 厂商列 | 我们放哪 | 字段 |
|---|---|---|
| 产品信息（缩略图、ASIN、价格、数量） | **表格第一列** | `task_products.image_url` / `asin` / `quantity` |
| 店铺信息 | 不做 | — |
| 订单信息（AMZ单号 + ASIN/邮编一致性勾叉） | 表格「错误码 / AMZ 单号」列 + 抽屉 | `tasks.amazon_order_no`；一致性校验见下 |
| 买家信息（收货人全套） | **抽屉「上游下发」段** | `tasks.ship_*` |
| 费用信息（运费/税前/税/总计） | **抽屉「采购结果」段** | `tasks.actual_shipping` / `actual_tax` / `actual_total` / `task_products.actual_unit_price` |
| 物流信息 | 抽屉「物流」段 | `logistics.shipments.*` |
| 买家号信息（环境名、买家号ID、卡后四位、同步时间） | 抽屉，拆两处 | `buyer_envs.code` 归「上游下发」；`tasks.payment_last4` 归「采购结果」 |
| 其他信息（状态、异常详情、备注、创建者、时间） | 表格状态列 + 抽屉事件时间线 | `tasks.status` / `task_events` |

商品主图用的是 `task_products.image_url`（m.media-amazon.com）。设计画布里画的是占位框——
画布不联外网，生产环境才真的加载图片。

**抽屉分两段是这次最主要的结构判断**：左边是上游发下来的、只读的、错了要去上游改的；
右边是采购跑完回填的、我们自己写的。厂商把这两类字段平铺在同一行里，
结果是运营看到一个不对的地址时，第一反应是在这儿改——但改完上游还是错的，下一单照错。

## 3. 订单详情弹窗：8 组字段逐个落点

厂商没有「详情页」——那一行本身就是详情，8 组字段横着铺开。我们把这 8 组**按同样的分组和顺序**
搬进点击才弹出的弹窗（列表里只留决策需要的那几列），末尾补上他们完全没有的事件时间线。

详情默认不展开。运营是在扫列表，不是在读单据；默认占掉右边 460px 只为了展示一条谁也没在看的记录。

### 3.1 店铺信息 → 上游订单

| 厂商 | 我们 |
|---|---|
| `storeName` | ✗ 不存。店铺留在上游 ERP，采购侧不需要知道是哪家店 |
| `orderNo` | `tasks.line_key` = sha256(上游单号\|asin)。他们是把两截字符串直接拼起来当主键，人眼分不出边界 |
| `country` | `tasks.marketplace`，首期恒为 `US` |

### 3.2 买家信息 → 收货信息（上游下发，只读）

`receivingName/Phone/Address/City/State/PostCode/Country` → `tasks.ship_name/ship_phone/ship_line1/ship_city/ship_state/ship_postcode/ship_country`，一一对应。

- `receivingDistrict` ✗ 日本站才必填，首期只有 US
- `platformPostCode` ✗ 影子字段，专门用来跟导入值比对。我们的地址是自己填进去的，没有第二份可比

### 3.3 产品信息

| 厂商 | 我们 |
|---|---|
| `imgUrl` | `task_products.image_url` |
| `asin` / `quantity` | `task_products.asin` / `quantity` |
| `price` | **换了语义** → `tasks.price_cap`。他们这是导入价，只摆着看；我们是限价，超了不采 |
| — | `task_products.actual_unit_price`，结算页实测单价。他们没有这一列 |

### 3.4 订单信息

- `platformOrderNo` → `tasks.amazon_order_no`，带部分唯一索引：同一个 AMZ 单号不可能落到两条任务上
- `asinCheck` / `postCodeCheck` ✗ 不存两份再打叉。回填那一刻断言，不符**直接不写**（`ORDER_NO_AMBIGUOUS`）

### 3.5 费用信息（来自 `purchaseOrderFinishUpdate`，深度分析 §5.1）

| 厂商 | 我们 |
|---|---|
| `shipping` / `tax` / `total` | `tasks.actual_shipping` / `actual_tax` / `actual_total` |
| `totalBeforeTax` | ✗ 不存，展示时算 `actual_total − actual_tax` |
| `subTotal` | ✗ 不存。他们这一列**恒为空**：插件里 `subtotal` 声明后从未赋值，且回传 key 是小写、面板读的是驼峰（深度分析 A12 / M7）。我们用 `actual_unit_price × quantity` 自己算 |

### 3.6 物流信息（来自 `updateTrackingInfo`，深度分析 §5.2，20 字段）

| 厂商 | 我们 |
|---|---|
| `platformTrackCarrier` | `shipments.carrier`。他们这个值是页面文本 `split(" ")[2]` 盲取第 3 个词 |
| `platformTrackNo` | `shipments.tracking_no` |
| `orderStatus` | `shipments.status`（`not_shipped` / `in_transit` / `delivered` / `cancelled`） |
| `deliveryTime` / `origDeliveryTime` | `tasks.delivery_date` / `delivery_raw`（原文必须留着，解析失败时的唯一线索） |
| `events[]` | `logistics.shipment_events` |
| `deliveryTimeAbnormal` | **换了做法**：他们是黄字提示、无系统动作；我们用 `max_delivery_days` 在下单前硬拦（`DELIVERY_TOO_LATE`） |
| `trackingHtml` | ✗ 不存。整页 HTML + 内联全部 CSS 的 base64，无长度上限。我们只存结构化事件 |

### 3.7 买家号信息

- `buyerAccount` → `buyer_envs.code`（值其实是防关联浏览器的环境名）
- `buyerCustomerId` → `buyer_envs.amazon_customer_id`
- `paymentCard` → `tasks.payment_last4`。**列必须是 text**：插件在识别到「用积分付」时会把这个字段直接写成中文「礼品卡」（深度分析 M9），按纯数字后四位建表会炸
- 同步时间 ✗ 没这概念。那是「等插件回传」的等待态；我们用 `plugin_instances.last_seen_at` + `task_events`

### 3.8 其他信息 → 执行信息

- `status` → `tasks.status`。他们 4 个，我们 7 个，多出 `claimed` 与 `manual`
- `failContent` → **换了做法**：`error_code` + `error_detail` + `task_events` 全流。一个自由文本字段换成 18 个封闭错误码加只追加的事件流
- `createTime` / `purchaseTime` → `tasks.created_at` / `purchased_at`
- `remark` ✗ 那是 Excel 导入的批次备注，我们没有导入通道
- `createName` ✗ 单子由上游下发，不是人在这里建的；本系统也不做鉴权，没有用户

### 3.9 截图里的两处，值得单独记一笔

**导入价 ≠ 实付价，而他们并排摆着却从不比较。** 产品信息写 `价格 13.99 · 数量 3`，
按说税前该是 41.97，可费用信息里税前总额是 `$37.77` —— 实付单价其实是 12.59。
这两个数在同一行里相距三格，没有任何提示。我们把产品信息那一格换成上游算好的限价，
并且在下单前拿实付跟它比。

**在途不该是红色。** 截图里物流状态「运输中」是个红标签。红色一旦用来表示正常在途，
真出事时就没有颜色可用了。我们的在途是天蓝虚线，红色只留给「坏了」。

## 4. 我们不抄的两样东西

**一致性校验双份存储**（`asinCheck` / `postCodeCheck` / 影子字段 `platformPostCode`）。
他们需要这个是因为数据是 Excel 搬进去的，导入值和同步值必须事后比对。
我们的订单本来就在自己库里，少一跳。ASIN 断言我们照做，但做法不同：
不存两份比对，而是在回填那一刻断言，不符就**不写**（`ORDER_NO_AMBIGUOUS`，见 `server/routes/tasks.py`）。
他们是「写进去再打个红叉给你看」，我们是「不确定就不写」。

**`priceCheck`**。他们接口返回这个字段，前端模板 0 处引用——护栏字段存在，界面不用，等于没有。
我们把它做成硬拦截：`actual_total > price_cap` 直接停在下单前，购物车清空，转人工。

## 5. 还没落到代码里的

画布上画了、但服务端接口还没写的（P4 admin API 的活）：

- 列表查询（分页 + 上面这些筛选条件）
- 批量单号解析与「没找到的号」回报
- 改地址 / 改 ASIN / 强制回填单号 / 重置回队列 这四个人工动作
- 实例判活阈值——目前只有 `/v1/instances/heartbeat` 上报端点，没有「多久算离线」

这几条在画布上都有对应的入口，实现时按画布上的语义来，不要另发明一套。
