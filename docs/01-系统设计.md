# AMZ 采购自动化系统 —— 设计文档 v0.3

> 技术栈：Python 3.12+ / PostgreSQL 17 / psycopg 3.2（裸 SQL，无 ORM）/ FastAPI；插件 Chrome MV3
> 执行模型：服务端派单，插件在防关联浏览器环境内执行
> 首期范围：**仅 US 站**
> 对齐基准：`ElijahRRR/WalmartAPI-Contral`（分层、registry、建表方式、命名与类型约定）
> 分析依据：厂商插件 v2.4.1 源码级分析（见 `ElijahRRR/AMZ-Purchase-Assistant` 的 `docs/插件功能深度分析.md`）

## 1. 架构与分层

沿用参考项目的**依赖只准自上而下**铁律，新增一个 `server/` 入口层：

```
cli.py    ─┐
           ├─→ workflows ─┐
server/   ─┘              ├─→ services ─→ api ─→ registry
                          │
        （server 不准 import workflows；任何层不准 import 入口层）
```

| 层 | 职责 | 禁止 |
|---|---|---|
| `cli.py` | 唯一命令行入口：加载 .env → 单实例锁 → 写 `ops.runs` → 执行 → 退出码 | 写业务逻辑 |
| `server/` | FastAPI 应用，插件的 HTTP 入口。只做请求校验 + 调 services | 写业务判断、import workflows |
| `workflows/` | 每文件一个 `run(params)`，对应一条可调度的业务链（ERP 同步、超时清扫、对账） | argparse、自行处理锁/通知 |
| `services/` | 跨入口复用的业务积木（任务编排、限价裁决、单号回填校验） | import server / workflows |
| `api/` | 外部系统适配（ERP 接口、通知） | 写业务判断 |
| `registry/` | 接线盒：`db.py`（连接唯一入口）、`paths.py`、`resources.py`、`settings.py` | 依赖任何上层 |

**为什么 server 和 workflows 同层**：两者都是入口，都会调 services。让 server import workflows 会把 HTTP 接口和调度链焊死，跟参考项目禁止 workflow 互相 import 是同一条理由。

## 2. 数据模型

**约定**（全部对齐参考项目）：

- 库名 `amz_purchase`，PostgreSQL 17
- 主键一律 `bigint GENERATED ALWAYS AS IDENTITY`，**不用 SERIAL**
- **不用 `CREATE TYPE ... AS ENUM`**；封闭集用 `text` + 行内注释
- 时间一律 `timestamptz`，存 UTC
- 建表脚本幂等（`CREATE SCHEMA/TABLE IF NOT EXISTS`），执行走 `python cli.py db_init`
- 改表**先改 `docs/db_schema.md`，再同步 `refdata/schema.sql`**

### 2.1 Schema 划分

| schema | 职责 | 写入者 |
|---|---|---|
| `procure` | 采购域：买家号、插件实例、采购任务、商品行、事件流 | task_intake / server / task_sweep |
| `logistics` | 物流域：运单与轨迹 | server（插件回传）/ shipment_sync |
| `ops` | 运行域：运行记录、游标 | cli.py 与各 workflow |

### 2.2 建表脚本

**不在本文档内联 DDL。** 表结构的唯一事实来源是 `docs/db_schema.md`，可执行镜像是
`refdata/schema.sql`（幂等），执行走 `python cli.py db_init`。

同一份 DDL 维护三处必然漂移——这正是厂商那套「文档说 `subTotal`、插件发 `subtotal`」
之类字段错位的来源。

改表流程：**改 `docs/db_schema.md` → 同步 `refdata/schema.sql` → `cli.py db_init` → 跑测试**。

### 2.3 与厂商 schema 的刻意差异

| 差异 | 理由 |
|---|---|
| `price_cap` 字段 | 厂商导入模板压根没有价格列（`逆向分析报告.md` 附录 D），这是他们做不出限价的根本原因 |
| 金额一律 `numeric` | 厂商全存字符串，还出现过 `"￥1,234\n(￥0)"` 二段式（分析 §M8） |
| 不设 `trackingHtml` | 厂商回传整页 HTML + 内联全站 CSS，单请求可达 MB 级（分析 §A13）。只存结构化事件，要凭证时按需重抓 |
| `line_key` 唯一约束 | 同一上游行不会重复建任务 |
| `amazon_order_no` 唯一索引 | 同一 Amazon 单号不可能落到两条任务上 |

## 3. 认领与超时清扫（简化版）

### 3.1 认领

```sql
WITH candidate AS (
    SELECT t.id
    FROM procure.tasks t
    WHERE t.status = 'ready'
      AND t.buyer_env_id = %(env_id)s
    ORDER BY t.created_at
    FOR UPDATE OF t SKIP LOCKED
    LIMIT 1
)
UPDATE procure.tasks
   SET status = 'claimed', claimed_by = %(instance_id)s,
       claimed_at = now(), updated_at = now()
  FROM candidate
 WHERE procure.tasks.id = candidate.id
RETURNING procure.tasks.*
```

一条 SQL 完成「选中 + 置位」，不存在「选完还没置位」的窗口。返回空行 = 当前无可派任务。

**这里没有跨实例互斥，是有意的。** 运营前提是同一买家号不会在两处同时登录拍单
（所有者定稿），因此不设租约表、不设顾问锁、不设 per-env 唯一索引。

`SKIP LOCKED` 保留，但要清楚它的职责边界：**它只避免行锁排队，不承担正确性职责**。
（v0.2 曾试图用一句 `NOT EXISTS` 充当互斥，实测证明在 READ COMMITTED 下挡不住并发——
详见 `02-schema-验证记录.md`。删掉互斥需求后这个问题随之消失，但那条实测结论值得留着：
**「看起来有护栏、实际防不住」比没有护栏更危险**。）

**登录态那道闸不在这条 SQL 里,是刻意的。** `daily_cap` 写成 SQL 的 WHERE 条件没问题
——「今天拍满了」和「今天没单」对插件来说处置一样(等下一轮)。但「这个买家号被登出了」
不一样:它需要人去做一件事。写成 WHERE 条件的话返回的是「没选中任何行」,
与「队列里确实没有单」渲染出完全一样的结果,插件继续每 10 秒问一次,
运营台上那台机器显示「待命」—— 而这**正是这条闸要修的那个缺陷本身**。
所以它是认领之前的一次单独 SELECT(同一条连接、同一个事务),被拦下时抛
`ClaimBlocked` → HTTP 409 `INSTANCE_SIGNED_OUT`。

实现见 `services/task_queue.py:claim()`。

### 3.2 超时清扫

`claimed` 超过 `claim_timeout`（默认 15 分钟）未回传，**不能简单退回 `ready`**——插件可能已经在 Amazon 上真下了单，只是没来得及回传。

```
claimed 超时
  └─ status = 'manual'，error_code = 'CLAIM_TIMEOUT'
     └─ 人工确认该买家号是否已产生订单
        ├─ 未产生 → 放回 'ready'
        └─ 已产生 → 回填单号 → 'purchased'
```

由 `workflows/task_sweep.py` 定时执行。

> 这是刻意保守。厂商系统在这里直接重捞，是重复下单的来源之一。

`workflows/task_retry.py`（有界自动重试，默认关）与这一条**方向相反、互不重叠**：
它只碰 `exception` 里 `RETRYABLE` 那一组，而 `claimed` 超时转出来的 `CLAIM_TIMEOUT`
属于「可能已下单」，永远不在它的选单里。见 §4.1。

## 4. 结构化错误码

替代厂商那套「18 处全是 `status=99` + 自由文本」（分析 §6.1）。

这张表的可执行镜像是 `services/error_codes.py`，`task_event.record` 与 `task_queue.fail`
都拿它校验——拼错的码直接拒收。改码先改这张表，再改那个模块，两边必须一字不差。

| code | 界面标签(= `error_codes.LABELS`) | 说明(只在这份文档里) | 可重试 |
|---|---|---|---|
| `OUT_OF_STOCK` | 商品无货 | 商品无货 | ✗ |
| `QTY_UNAVAILABLE` | 目标数量不可选 | 目标数量不可选 | ✗ |
| `ADD_TO_CART_FAILED` | 加购后未跳转 | 加购后未跳转 | ✓ |
| `BUNDLE_PRODUCT` | 捆绑商品,需人工 | 捆绑商品,需人工 | ✗ |
| `NOT_FBA` | 配送方非 Amazon | 配送方非 Amazon | ✗ |
| `CART_MISMATCH` | 购物车与任务不符 | 购物车与任务不符 | ✓ |
| `ADDRESS_FORM_TIMEOUT` | 地址表单加载超时 | 地址表单加载超时 | ✓ |
| `ADDRESS_STATE_UNMATCHED` | 州匹配失败 | 州匹配失败 | ✗ |
| `ADDRESS_SUGGESTION_BLOCKED` | Amazon 提示地址不可投递 | Amazon 提示地址不可投递 | ✗ |
| `ADDRESS_NOT_APPLIED` | 地址填了但没生效 | 地址填了但页面仍显示别的地址 | ✗ |
| `PRICE_CAP_EXCEEDED` | 货款超限价 | 货款(实付 + 礼品卡抵扣)超过整单限价 | ✗ |
| `PAYMENT_METHOD_UNEXPECTED` | 支付卡不符 | 结算页选中的卡与 `buyer_envs.expected_card_last4` 不符（留空 = 不校验）。归 `BUSINESS_BLOCKED`：处置是改配置或去买家号里换回那张卡，重试多少次结果都一样，也不涉及「可能已经下单」——这道闸在下单**之前** | ✗ |
| `DELIVERY_TOO_LATE` | 交期超限 | 交期超限 | ✗ |
| `DELIVERY_UNPARSEABLE` | 交期无法解析 | 交期无法解析 | ✗ |
| `CHECKOUT_TIMEOUT` | 结算页跳转超时 | 结算页跳转超时 | ✓ |
| `ORDER_CONFIRM_TIMEOUT` | 下单后未见确认页 | 下单后未见确认页 | ✗（可能已下单） |
| `PAYMENT_VERIFICATION_TIMEOUT` | 发卡行验证超时 | 发卡行验证超时：下单后 Amazon 把结算 iframe 导到 3DS 验证页，操作员没在时限内做完 | ✗（可能已下单） |
| `ORDER_NO_AMBIGUOUS` | 无法确定哪个单号属于本单 | 无法确定哪个单号属于本单:diff 出 0 或 >1 个新单,或订单卡 ASIN 与本单不符 | ✗ |
| `CAPTCHA_ENCOUNTERED` | 命中验证码/风控 | 命中验证码/风控 | ✗ |
| `CLAIM_TIMEOUT` | 认领超时未回传 | 认领超时未回传 | ✗ |
| `PLUGIN_INTERNAL` | 插件内部异常 | 插件内部异常 | ✓ |

**「界面标签」这一列就是 `services/error_codes.LABELS`，一字不差**，`tests/test_task_event.py`
逐码比对。全项目只有这一份标签：`/v1/admin/meta` 下发的是它，运营台列表与详情、
插件面板渲染的也是它。界面上不出现英文码 —— 英文只在库、日志和 API 里露面。

在此之前这一列是**一列死数据**：下发的是「含义」那一列，21 个码里 8 个两边不是同一句话，
而且没有任何测试比过它。照那一列去改标签的人，会改一个没人读的地方。
现在两列的分工是明确的：**左边那列是代码里的字面量**（改标签先改 `error_codes.py`，
再改这里，两边必须一字不差）；**右边那列是给读这份文档的人看的长解释**，
它**不参与比对**，也不出现在任何界面上。

**`PAYMENT_VERIFICATION_TIMEOUT` 为什么不并进 `ORDER_CONFIRM_TIMEOUT`。**
两者的现场完全不同：前者是**订单已经提交给 Amazon、正卡在发卡行验证**（结算 iframe 落进
不透明源，读 `location` 抛 SecurityError），后者常见的成因是根本没点动那个按钮。
处置也不同 —— 前者要去催操作员完成验证、事后必须去买家号里查一遍（钱很可能已经扣了），
后者多半重置一下就行。合成一个码的话，「我们这个月因为 3DS 丢了多少单」只能去翻
`task_events` 的 payload，而按码建的处置 SOP 会把两件事混为一谈。
它与 `ORDER_CONFIRM_TIMEOUT` 同属 `TO_MANUAL` + `POSSIBLY_ORDERED`：重置前必须有人
去买家号里确认过，那道二次确认闸(NEEDS_ACK)照样拦着它。

**登录态失效**(页面落到 `/ap/signin`)**刻意不在这张表里。**
它回答的不是「这一单为什么失败」——单子本身没毛病，是那台机器的浏览器被登出了。
处置是**退回队列**(还没到下单点时)，`tasks.error_code` 一个字都不会写；编一个码
进去，它会永远停在 0 次出现，还得硬塞进下面三组之一。登录态是**实例的一个字段**
(`procure.plugin_instances.login_state`，封闭集 `ok` / `signed_out` / `unknown`)，
有自己的界面标签和自己的那道认领闸，见 `docs/03-运营台字段对照.md` §5.3。

**两条硬规则：**

1. 任何终止执行的路径都必须调 `/fail` 或 `/release`。不允许「只写本地日志」——厂商系统有 30+ 条这种路径（分析 §6.3）。
2. `/fail` 之后插件**必须清空购物车**再释放。厂商多数失败路径不清车，一次失败连带废掉下一单（分析 §C2）。

### 4.1 「可重试」这一列现在真的有东西在读它

`workflows/task_retry.py` 会把 `RETRYABLE` 那一组的 `exception` 退回 `ready`。
在此之前这一列只是个形容词：没有任何 workflow 消费它，界面因此**不许**写「系统自己会再试」。
现在它有了消费者，但每一条边界都是封死的：

- **默认关**：`AMZ_AUTO_RETRY_MAX=0`。要开就在 `.env` 里写个数，命令行参数打不开它——
  「默认关」要是能被一句 `-p` 绕开，那它就不是默认关，而是「取决于谁在敲命令」。
- **有界**：同一张任务**一生**最多被系统自动重那么多次（`tasks.retry_count` 只增不清），
  且失败后至少隔 `AMZ_AUTO_RETRY_BACKOFF_MIN` 分钟（默认 10）才轮得到它。
  人点的重置**不占**这个数，但也不清零。
- **一轮也有界**：`AMZ_AUTO_RETRY_BATCH`（默认 20）限这一轮最多放几条回队列，
  `AMZ_AUTO_RETRY_MAX_AGE_MIN`（默认 1440 = 24 小时）之外的失败**不再自动重**。
  两道拦的是同一个场景：把上限从 0 改成 N 的那一轮，库里积着的**全部历史** `exception`
  的 `retry_count` 都是 0、都早过了 backoff，会一次性全部退回队列，插件挨个在亚马逊上
  重拍一遍——`retry_count` 在那里一点忙都帮不上，它界的是「同一张单重几次」，
  不是「一轮放几张单」。条数上限只把这一批摊到几轮里，真正拦住它的是年龄闸：
  攒了几个月的失败单多半已经在别处处置过了（上游取消了、有人手工买了），
  不该由一条定时任务替人重新买回来。
- **只碰 `exception`，不碰 `manual`**：`manual` 的含义就是「等人裁决」，系统在那儿替人做决定，
  那道闸就白设了。这也是它与 `task_sweep` 的分工：那一条清扫 `claimed` 超时且**刻意不退回 ready**。
- **走的是与人工重置同一个函数**（`services/task_admin.reset_to_queue`，`by=manual/auto`）。
  另写一条 `exception → ready` 等于把 `NEEDS_ACK` 那道闸绕过去，而且两条路迟早分叉——
  这一条分叉的后果是重复下单。
- **`POSSIBLY_ORDERED` 那三个码永远走不到这条路**，共四道：选单前断言两组不相交
  （相交就**整轮拒绝**，不是悄悄过滤掉）；SQL 里再排除一次；执行前逐条再判一次；
  最后是 `reset_to_queue` 那道 `NEEDS_ACK`——自动重试连带回执的资格都没有
  （`by=auto` + `acknowledged=True` 直接被拒），因为回执的含义是**有人去订单页看过了**。
- **事件流分得开**：人点的落 `kind='admin'`，系统重的落 `kind='auto_retry'`，
  载荷里带 `attempt/max`。出现重复下单时，「是谁把它放回队列的」是第一个要问的问题。
- **界面文案跟着配置走**：`GET /v1/admin/meta` 下发
  `auto_retry: {enabled, max, backoff_min, max_age_min, batch}`。
  `max_age_min` 也必须下发：它决定的不是「什么时候重」，而是**会不会重**——
  界面不知道这道闸，就会对着一张系统永远不会碰的单继续写「不点它也会被放回队列」。
  关着说「需人工重置」，开着说「系统最多自动重试 N 次（已试 k 次）」。
  **不许在任何一侧写死一个「做没做自动重试」的布尔**——功能做出来之后，
  开没开就是配置的事，写死的那份迟早与配置说的不是同一件事，而两个方向都会让界面撒谎。
- 开着才算「必须定时」：没开的时候这条链每轮安静跳过，运营台的工作流记录页不为它标红
  （照 `feishu_writeback` 的先例，一格永远红着的卡片会把人训练成忽略红色）。

## 5. 护栏

### 5.1 限价

插件在结算页采集实测值，提交给服务端裁决：

```
goods_total = actual_total + gift_card_amount      ← 服务端自己算
goods_total > price_cap  →  PRICE_CAP_EXCEEDED  →  不下单,清车,转 manual
goods_total ≤ 0          →  PLUGIN_INTERNAL     →  同上
```

阈值在服务端，改限价不需要发新插件版本。

**护栏比的是「这一单的货款」，不是「这张卡要扣的钱」。**

结算页 `#checkout-pyo-button-block .grand-total-cell` 上写的是后者。
买家号里躺着礼品卡余额时，它是抵扣**之后**的数——全额抵扣就是 `$0.00`。
拿它比限价，护栏在任何用礼品卡的买家号上整体失效，而库里和界面上一切正常：
实测一张货款 `$2,241.86`、礼品卡垫了 `$1,100` 的单，`price_cap=$1,200` 照样放行，
库里落一个 `actual_total=1141.86`，运营台画绿点写「未超」。

礼品卡怎么认：`input[name="subtotalLineType"][value="SPECIAL_PAYMENTS_GIFT_CARD_BALANCE"]`
（判据是隐藏表单标记，与页面语言无关；出处厂商 v2.5.3 `popup.js:2052-2079`，
这是这次从他们那儿最值得抄的一条）。

三条边界，每一条都有测试盯着（`tests/test_price_guard.py`）：

- **`applied` 与 `amount` 是两个独立的事实。** 认出抵扣行却读不出金额时
  `amount` 是 `null` 而不是 `0` ——「抵扣 0 元」与「不知道抵扣多少」不是一件事，
  后者直接 `PLUGIN_INTERNAL` 拒掉：货款基数算不出来就不下单。
  退回去当成「没有礼品卡」是最坏的选择，那会让护栏拿一个偏小的数去比。
- **下界。** 在此之前 `adjudicate` 只有「读不到就拒」和「超限价就拒」，
  `0.00` / `0` / `-5.09` 三种取值实测**全部放行**。现在判的是**货款** ≤ 0
  ——礼品卡全额抵扣的单实付确实是 `0.00`，那是对的；货款为 0 只可能是
  金额还在 shimmer，或者选择器读错了格子。
- **服务端自己算，不采信插件报的 `goods_total`。** 插件也报一份，
  但那份只用来对账（两边不一致时记进事件流）。把基数交给被管的一方算，
  闸门就不成其为闸门。

`tasks.gift_card_amount` / `tasks.goods_total` 在 guard-check 那一步落库，
**不管放不放行**——被护栏拦下的单同样要能答出「当时比的是哪个数」。

### 5.1.1 自洽记录(不是护栏)

`adjudicate` 收下 `line_items` 之后会算一次 `Σ单价×数量` 与货款的差，
超过 `AMZ_PRICE_CONSISTENCY_TOLERANCE_PCT`（默认 15）就在 `guard_check`
事件的载荷里留一句 `consistency_note`。

**它不拦单。** 结算页面板上的单价是税前、不含运费的，与货款天然有差
（夹具那张单差 8.6%），拿它当闸会把正常单拦一片。
它答的是另一个问题：「这一单有几件商品的价格我们其实没看见」——
Amazon 改版后单价选择器只对第一个面板生效时，`priced.length=1` 不为 0，
插件那条「一个都没读到」的告警不触发，而库里第二件的 `actual_unit_price`
是 NULL、运营台上半列空着，没有任何地方说明为什么。

阈值默认 15% 而不是更紧：一条**每单都出现**的告警等于没有告警
（与 `feishu_sync` 那格「永远红着的卡片」同一个理由）。

### 5.2 交期

厂商的实现被 6 处日期解析缺陷架空（分析 §8.3）。本系统：

- **插件只上报 `delivery_raw` 原文，不做解析**
- 服务端解析，以站点时区（US → America/Los_Angeles）为基准
- 解析失败 → `DELIVERY_UNPARSEABLE` → 转人工，**不放行**（厂商那边解析失败时弹窗让操作员选「继续下单」，等于把护栏交给疲劳的人）
- 解析出的日期早于今天 → 视为解析错误，同样转人工（直接防住厂商那个「超过一个月就减一年」导致的负数天数放行）

首期需覆盖的 US 文案：`Tomorrow` / `Thursday, August 27` / `August 27` / `Aug 27` / `Sept 12` / `Aug 21 - Sep 5`（**取结束日**）

**解析顺序**（`services/delivery.parse_delivery`，前五条对着厂商的缺陷写，后三条是我们自己踩出来的）：

1. 黑名单先判——`Arriving after Christmas` 这类不该被后面的规则蒙对
2. **区间取结束日**。连字符两侧有没有空白都算区间：`Sep 8 - Sep 20` / `Sep 8 - 20` /
   `Sep 8-20` / `Sept 8–20` 必须收敛到同一个日子。我们自己曾经只认带空白的那种，
   于是**差两个空格就换一个结论**——实测同一个区间，一种写法拦截 `DELIVERY_TOO_LATE`（14 天），
   另一种放行（2 天）。区间正则要求**连字符左边必须有月名**，`2-4 business days`
   和 ISO 串 `2026-09-08` 都碰不到它
3. **带年份优先于不带年份**
4. **月日优先于星期几**，也优先于相对词
5. 不带年份时**向未来取最近的一年**
6. **同一段文案里有多个月日取最晚的那个，不是第一个**。`Ships Sep 3, arrives Sep 12`
   的第一个是发货日；与「多条交期取最晚」是同一个立场，不该只在跨条时成立
7. **向未来滚年有上界**（`MAX_FUTURE_DAYS = 300` 天）。没有它，上面那个已经过去的
   `Sep 3` 会被滚成 `2027-09-03` 写进 `tasks.delivery_date` 并印在运营台详情上——
   一个 **Amazon 从未给出的日期**，却带着具体到日的可信外观。人去核对时会先怀疑
   亚马逊页面，而不是我们的解析器。超界返回 `None` → `DELIVERY_UNPARSEABLE` 转人工。
   这个上界**只管我们推断出来的年份**，页面白纸黑字写了年份的照它写的算
8. **显式日期优先于相对词**：`Tomorrow, September 8` 按页面写出的 9/8 算，不是 today+1。
   服务端算的站点当天与 Amazon 页面翻页的时刻不会永远一致（美西已经 9/7、我们还是 9/6），
   差这一天会同时进闸门判定和回填的 `delivery_date`，在 `max_delivery_days` 边界上
   把一单本该拦下的放行，而库里记的日期与亚马逊订单页对不上——表现为一种查不出根因的
   系统性偏移。相对词排在显式日期之后、星期几之前

读到了月日却定不出一个可信年份时**返回 `None`，不再往下猜**（不回退到相对词或星期几）：
页面明明写了日子而我们读不懂，那就是该交人工的情形，蒙一个日期出来正是厂商那套
「解析失败弹窗让人选继续下单」的另一种形状。

|---|---|
| FBA | 配送方文案须匹配 Amazon 自营。开关是 `tasks.require_fba`（默认 true）——**它现在真的是一列**：在此之前库里没有这个字段，路由也不往 `adjudicate` 传，走的是函数签名里的默认 `True`，于是一道号称「可关」的闸恒为真，照文档去关它的人会发现改哪儿都不生效 |
| 地址一致 | 结算页地址须含 `ship_postcode` **且含收件人姓氏**（厂商只查邮编子串，分析 §4.2.4） |
| 地址建议弹窗 | 出现即 `ADDRESS_SUGGESTION_BLOCKED` 转人工。厂商一律选「原始地址」强行提交（分析 §A7） |
| 数量 | 从**结算页真实读取**并比对（厂商那处比对是恒真的死代码，分析 §A6） |
| 支付方式 | 结算页选中的卡尾号须等于 `buyer_envs.expected_card_last4`；不符即 `PAYMENT_METHOD_UNEXPECTED`，**在下单之前**。留空 = 这个买家号不校验（闸是可关的，与 `require_fba` 同形态）。**读不出来也算不符**——「读不出来就放行」的闸，在选择器被改版打掉那天会无声失效。<br>**只读不写。** 厂商 v2.5.3 `popup.js:2229-2310` 会点开 payselect 页替买家号勾选指定尾号的卡再确认下单，依据是插件本地 localStorage 里一个操作员随手能改的输入框。我们不做：改一个买家号的支付配置是**人**的动作，不是拍单流程的动作；不符就转人工。<br>**槽位数也算一条判据。** `payment_last4` 只答得出**第一个**已选支付方式里那张卡；Amazon 允许把一单拆到多个支付方式上，那时第一张对得上、第二张刷了多少这道闸完全不知道，而运营看到的是一道「已核过支付卡」的绿灯。插件报 `payment_slots`（可见槽位数），服务端扣掉礼品卡余额占的那一个之后 `> 1` 即判 `PAYMENT_METHOD_UNEXPECTED`。槽位数没报上来（老插件）就退化成只校验第一张卡；买家号没配期望卡时整条支付判据都不看，不留「卡不校验但槽位校验」这种半开状态 |
| 日限 | `buyer_envs.daily_cap` 达标后不再派单 |
| 回填 ASIN 断言 | 三态：对上 / 不符（**不写单号**，转人工）/ **一个都没采到**（照旧回填，但落一条 `assert_skipped` 事件，近 7 日计数上运营台）。展开见 §6 |
| 登录态 | `plugin_instances.login_state = signed_out` 的实例认领时被拒(`INSTANCE_SIGNED_OUT`)。判定不读 Cookie，只读导航栏；判不出来是 `unknown`，**不当成 `ok`** |

### 5.4 越过下单点的那道闸（`tasks.may_have_ordered`）

「点下单那一刻起禁止退回队列」这条铁律，插件那一侧一直是对的：`mayHaveOrdered`
在 `placeOrder()` **之前**置位，置位之后任何失败都 `to_manual`。
**服务端那一侧曾经漏了一整类。** 重置回队列的 `NEEDS_ACK` 闸按
`error_code ∈ POSSIBLY_ORDERED` 判，而越过下单点之后落下来的码不一定在那一组里：

```ts
const code = e instanceof Abort || e instanceof DriverError
  ? e.code                                    // ← 驱动认得出原因就直接用它的码
  : (mayHaveOrdered ? "ORDER_CONFIRM_TIMEOUT" : "PLUGIN_INTERNAL");
```

点完下单按钮之后 `readOrderCard()` 抛 `DriverError`，落库就是
`status=manual` + `error_code=PLUGIN_INTERNAL`：**状态说「要人裁决」，码说「重一下就过」**。
判码的闸放行，人点一下重置，这张已经花过钱的单被再买一遍——而运营台上那条紫色警告
（同样按码渲染）压根不会出现，人连该去哪儿确认都不知道。

所以事实自己要在库里留一行：

- 插件在 `placeOrder()` **之前**上报
  `kind='step'`、`payload={"step":"点击下单按钮","may_have_ordered":true}`，
  **并且这一条是下单的前置条件，不是旁白**：`client.events` 走的是一次不重试的 POST，
  撞上网络抖动 / 服务端重启 / 15 秒超时就回 `{ok:false,kind:'transport'}` ——
  丢掉返回值照点的话，单在 Amazon 上真下成了而库里那一位从没被置上，
  下面四道闸一起失效（触发条件不再是「键名写错」，而是「那一次 POST 没说上话」，
  后果一模一样）。所以：没落地就重发一次（服务端那条 UPDATE 幂等），
  还不落地就**不点** —— 清车、`/release` 退回队列，那一刻还没花钱，这一边是安全的。
  `mayHaveOrdered` 在**确认落地之后**才置位，随即点下单。
  （`/release` 被 409 `POSSIBLY_ORDERED` 拒掉也是对的：那说明第一次其实落了库、
  只是响应没回来，任务停在 `claimed` 等清扫转人工 —— 比退回队列更该走的那条路。）；
- `POST /v1/tasks/{id}/events` 收到这条就把 `tasks.may_have_ordered` 置 `true`，
  **追加事件与置位在同一事务**——分开写会留下「事件流写着点过下单按钮、而闸门那一列
  还是 false」这种留了痕却没人认的痕，比不留更坏；
- 只往 `true` 写，**重置回队列不清它**：「曾经花过钱」是既成事实，
  不会因为它又排回队列而变回没花过；
- 闸判两条判据取**或**：`error_code ∈ POSSIBLY_ORDERED` **或** `may_have_ordered`。
  人工重置、批量重置（`skipped` 清单里带上这一列，只报错误码的话看的人会以为系统抽了）、
  自动重试选单（`services/task_retry.candidates()` 的第 ④ 条）三条路各判一次；
- **回到队列的第四条路是插件自己调的 `POST /v1/tasks/{id}/release`，它也判**：
  越过下单点之后一律 409 `POSSIBLY_ORDERED`，任务停在 `claimed` 不动，
  由 `task_sweep` 按 `CLAIM_TIMEOUT`（在 `POSSIBLY_ORDERED` 组里）转人工。
  上面三条至少还要人点一下，这一条**连人都没有**：插件版本旧了、`run.ts` 里那个
  `if (!mayHaveOrdered)` 被人改坏、或者另写了一条清理路径，任务就原地回到 `ready`，
  下一次 `claim` 立刻把它再派出去。判据放在路由层而不是 `task_queue.release`
  的 `WHERE` 里：那个函数返回 `False` 会被渲染成 `TASK_NOT_HELD`——**说错了原因**，
  插件日志里留下的是「这一单已经不在我手上」，而真相是「它在你手上，但你不许放手」。
  拒之前先落一条 `assert_failed`（`reason=release_after_order_line`）：
  插件试图退回这样一张单，本身就是插件那侧漏判的证据。

`NEEDS_ACK` 那句「为什么拦你」**有两种措辞**：码触发时说码，越过下单点触发时说
「这一单已经越过下单点（下单按钮点过了）」。运营台那条二次确认条**原样渲染服务端
这句话**，不再自己按 `error_code` 编——编出来的那句对「码人畜无害、拦它的是越过
下单点」那一类单是**假话**（`PLUGIN_INTERNAL` 并不意味着下过单，运营会照它学到
一条错误的规则），而真正的理由只在被丢掉的那句 message 里。上方那条紫色警告条
同样按码渲染，对这一类单压根不出现，所以确认条是唯一说话的地方。
这句话因此要自己把话说全（含「重置 = 再买一遍」这个后果），
且不许出现 `acknowledged` 这种接口参数名——那是给程序看的，不是给人看的。

这条契约的**每一半都有测试盯着**：服务端认的键名与文档对不对得上是一条；
`extension/src/flow/run.ts` 里**真的在 `placeOrder()` 之前发了那条 step** 是一条；
**那条 step 的返回值真的被消费了**（没落地就不点）又是一条 ——
后两条都直接读 `.ts` 源码比对（照 `tests/test_login_state.py` 的先例），
而且**先剥掉注释再比**：同一处的注释里就写着这个键名，不剥的话把代码里的键名
改成 TS 习惯的 `mayHaveOrdered`，子串搜索照样命中注释，全套测试仍然全绿 ——
一条以「防键名分叉」为名的测试自己变成了招牌。
「没落地就不点」那一半另有一条行为测试（`extension/test/unit.test.mjs`：
events 回 transport 失败时 `placeOrder` 一次都不许被调用）。读源码那几条不能省：
上面四道闸没有一道自己看得出「越过下单点了」，全都在等这个**键名**；
写成 TS 习惯的 `mayHaveOrdered`、或者那一行漏了，
`payload.get("may_have_ordered") is True` 恒为 `False`，闸整体退化成一块
**永远不动的招牌**——而服务端侧的测试全是自己用 HTTP 合成那条事件的,一条都不会红。

自动重试那条为什么也要判：`status` 是**插件**在 `/fail` 里用自己算的布尔定的
（`manual = mayHaveOrdered || toManual(code)`）。插件版本旧了或者两边分叉，一张点过
下单按钮的单会落成 `exception`，而它的码恰恰在 `RETRYABLE` 里——那一轮的后果不是报错，
是**定时任务自动重复下单**。这一列不经插件的判断，记的是它自己说过的话。

## 6. 下单成功判定与单号回填

**取订单历史第一张卡**——沿用厂商做法。所有者以几万单实测背书：面板侧的
`asinCheck` / `postCodeCheck` 本就是比对「导入值 vs 同步值」的机制，回填错会亮红叉，
几万单未出现，说明在该运行条件下这个假设成立。因此**不做下单前订单号快照**
（那会多一次页面加载）。

两处仍然收紧，都是零成本的：

| 收紧 | 做法 | 理由 |
|---|---|---|
| 成功判定 | **只认** URL 命中 `/gp/buy/thankyou/` | 厂商把「回到 `/gp/cart/view.html`」也判成成功，而弹回购物车恰恰是下单失败的典型表现。只认 thankyou 严格更正确且无代价 |
| ASIN 断言 | 那张卡的商品链接**本来就要解析出 ASIN**，顺手比对是否属于本单 | 不多一次页面加载、不改主流程。不符则记 `assert_failed` 事件并转 manual，而不是静默写库 |

**这道断言是三态的**（`services/order_backfill.asins_match`）：

| 结果 | 处置 | 事件 |
|---|---|---|
| `match` | 照常回填 | — |
| `mismatch` | **不写单号**，转 manual | `assert_failed` |
| `not_observed`（一个 ASIN 都没采到） | **照旧回填**（既定取舍：断言的职责是抓错配，不是制造噪音） | `assert_skipped` |

第三态原本与第一态**返回同一个值**（`if not observed: return True`），于是调用方只有一个分支，
这两件事在事件流里、库里、任何统计里都长得一模一样。而它们的含义正好相反：
一个是「比过了，是本单」，一个是「压根没比」。

危险在于第三态**会整体发生**：Amazon 某次改版把订单卡的商品链接换个类名，
插件采到的 ASIN 恒为 `[]`，而订单号本身仍读得出来——断言于是退化成厂商那套
「盲取第一张卡」，回填照常成功，**没有任何一条错误码提示护栏已经不工作了**。
若此时订单历史页还没刷出本单（或本次下单其实失败、第一张仍是上一单），
写进去的就是**上一单的 Amazon 订单号**——正是我们在 README 里指着厂商说的那件事。

所以取舍保留（不阻断），可见性补上：`assert_skipped` 事件带 `expected` 与
`amazon_order_no`，近 7 日计数由 `GET /v1/admin/error-stats` 的 `assert_skipped` 字段
下发，显示在运营台的错误码分布页上。**窗口固定 7 天，不跟着那一页的时间范围走**——
它回答的不是「这段时间出了什么事」，而是「那道断言现在还工作吗」。

**这个数必须连同同期的回填条数一起下发**（同一条 SQL、同一个窗口的两个 `count`）：
近 7 天回填 500 单漏了 1 单（页面没渲染完，无害）与 近 7 天只回填 1 单、这 1 单漏了
（选择器已坏，断言 100% 失效），`count` 都是 1——只发这一个数，两种相反的情况在界面上
**渲染成同一个结果**，而界面还会让人去别的页面手工数分母。比例与「要不要报警」
（`ratio` / `alert`，阈值 `ASSERT_SKIPPED_ALERT_RATIO = 20%`）也在服务端算好：
界面不把除法留给人做，阈值也不在前端存第二份。琥珀挂在**比例**上而不是 `count > 0`——
后者会让那张卡片常年琥珀，而一张常年琥珀的卡片会把人训练成忽略它，
恰恰在它真该报警的那一天。`backfills = 0` 时 `ratio` 是 `null` 而不是 `0`：
「这几天没回填过」与「回填很多次、一次都没漏」是两回事。
（它在原有的 `error` / `guard_block` 两个统计口径里一条都不会出现——
断言被跳过既不是失败也不是拦截，恰恰是一批**看着完全正常的 `purchased`**。）

库层再加一道：`uq_tasks_amazon_order_no` 唯一索引——同一个 Amazon 单号不可能落到
两条任务上，回填写错时直接被拒绝。

## 7. HTTP 契约

无鉴权。所有响应统一 `{"ok": bool, "data": ..., "error": {"code","message"}}`。
请求/响应模型定义在 `server/schemas.py`（Pydantic），是插件契约的**唯一**定义处。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/instances/register` | 登记实例身份，返回 `instance_id` |
| POST | `/v1/instances/heartbeat` | 上报存活 + 这一轮读到的登录态(不带 = 没有新消息);回 `login_check_due`:该不该去读一次页面 |
| POST | `/v1/tasks/claim` | 认领一条任务（body 带 `env_code`），返回任务详情 + 护栏参数。被登出的实例回 409 `INSTANCE_SIGNED_OUT` ——**不是**回一个「没有单」 |
| POST | `/v1/tasks/{id}/events` | 上报执行步骤（可批量） |
| POST | `/v1/tasks/{id}/guard-check` | 提交结算页实测值，请求裁决 |
| POST | `/v1/tasks/{id}/complete` | 下单成功 + 单号 diff 结果 |
| POST | `/v1/tasks/{id}/fail` | 结构化失败上报 |
| POST | `/v1/tasks/{id}/release` | 主动放弃（不算失败，退回 ready） |
| POST | `/v1/shipments/sync` | 物流轨迹回传 |

`claim` 响应即插件执行所需的全部输入：

```jsonc
{
  "ok": true,
  "data": {
    "task_id": 10234,
    "marketplace": "US",
    "shipping": { "name": "…", "phone": "…", "line1": "…",
                  "city": "…", "state": "CA", "postcode": "92707", "country": "US" },
    "products": [{ "asin": "B0FB3VS68J", "quantity": 1 }],
    "guards": { "price_cap": "12.50", "max_delivery_days": 7, "require_fba": true }
  }
}
```

## 8. 插件设计

### 8.1 与厂商插件的关键差异

| 维度 | 厂商 v2.4.1 | 本系统 |
|---|---|---|
| 代码组织 | 单文件 3,615 行，无构建 | TypeScript + Vite，模块化，可测 |
| 权限 | `*://*/*` + `cookies` + 3 个死权限 | 仅 `*://*.amazon.com/*`，**不申请 `cookies`** |
| 护栏 | 写死在插件里 | 服务端下发 + 服务端裁决 |
| 失败上报 | 18 处 `99`，另 30+ 处不报 | 全部结构化上报 |
| 并发保护 | 一个会泄漏的全局布尔量（会死锁） | 服务端 `claimed` + 本地单飞锁 |
| 超时 | 多处无超时/无法命中的超时 | 统一 `withTimeout()`，**每个等待都有上限** |
| 弹层 | 失败路径不关，堆积活 checkout | `try/finally` 强制关闭 |
| 选择器 | 60+ 个散落全文 | 集中注册表，命中失败上报 `SELECTOR_MISS:{id}` |

### 8.2 执行时序

```
心跳循环(顺带上报登录态:服务端说「有单在等、且该复检了」时,
          认领之前先开一张轻量页面读导航栏 —— 不读 Cookie)
   ├─ 读到 signed_out → 这一轮不认领,面板显示「已登出」,等人重新登录
   └─ POST /tasks/claim
        ├─ 无任务 → 等下一轮
        └─ 有任务
             ├─ 本地单飞锁
             ├─ 清空购物车(起点必须干净)
             ├─ for each product: 加购(每步 withTimeout)
             ├─ 购物车核对(条目数 + ASIN + 真实数量)
             ├─ 结算 → 填地址 → 保存
             ├─ 抓 before[]
             ├─ 采集结算页实测值 → POST /guard-check
             │     ├─ 放行 → 继续
             │     └─ 拦截 → 清车 → POST /fail
             ├─ 上报 step「点击下单按钮」(may_have_ordered=true) —— **点之前**发
             ├─ 点 Place Order → 三段有界等待(见 §8.3)→ 只认 thankyou 页
             ├─ 抓 after[] → diff
             ├─ POST /complete
             └─ finally: 关闭所有弹层 + 释放

任何一步发现页面落到 /ap/signin:
   ├─ 还没到下单点 → 事件流记一条 step「登录态失效,退回队列」→ 清车 → /release
   │                  (**不记异常** —— 这一单没毛病,是环境坏了)
   └─ 已越过下单点 → 走既有的转人工路径不变(「可能已经花了钱」更要紧)
   两条都把登录态标成 signed_out 上报,下一次认领因此被服务端拦住
```

`finally` 是硬要求。厂商插件失败路径不关弹层，10 单失败就堆 10 个活着的 checkout 会话（分析 §10.6）。

### 8.3 点了下单之后的三段等待

美国站的真单会遇到发卡行验证（3DS）：点 Place Order 之后 Amazon 把结算 iframe
导到 WorldFirst / Mastercard ID Check 的**跨域**页面，要操作员去手机上收一条短信、
回来输验证码。这一段与流水线上别的等待不是一回事，所以它单独有一套形状：
**有界、分段、可见、上报**，四件缺一不可。

```
点了下单按钮
   │
   ├─ normal        预算 T.orderConfirm(60s)。页面读得到、还不是确认页 → 继续等
   │     └─ 读 location 抛 SecurityError(落进不透明源)→ 进 manual_verify
   │
   ├─ manual_verify 预算 T.manualVerify(默认 6 分钟)
   │     · 进入的那一刻:把 iframe 连同一条中文横幅**推到屏幕中间、可点**
   │     · 上报 step {state: manual_verification, deadline_ms}
   │     · 面板起 verify 相位 + 倒计时,运营台列表挂「等人工验证」徽标
   │     · **不重置总时钟**
   │     └─ 页面重新读得到 → 进 post_verify;读到 thankyou → 成功
   │
   └─ post_verify   预算 T.postVerify(60s),独立且短
         · 验证做完了(或被拒了),页面正在往下走
         · 上报 step {state: manual_verification_done}
         · 厂商 v2.5.3 在这一格是**永久卡死**:他们把两处结算导航的
           maxWaitTime 改成 0,唯一出口只剩「URL 连续稳定」与「iframe 失效」

任何时刻 iframe 不在了 → 立刻 ORDER_CONFIRM_TIMEOUT(detail 写明是哪一种读不到)
总时长再压一道硬顶 = min(T.orderHardCap, 认领时刻 + claim_timeout_min×60s − 3 分钟余量 − 此刻)
```

**上界为什么必须由服务端反推。** `task_sweep` 只看 `claimed_at`，插件发再多 step
事件也不会推迟清扫。插件自己拍一个上界的话，会撞上所有结局里最坏的一个：
第 15 分钟任务被转成 `manual`/`CLAIM_TIMEOUT`，第 16 分钟操作员做完验证、订单真下成了、
单号也读到了，`complete` 却拿回 409 `TASK_NOT_HELD` —— **钱花了、货发了，
系统里是一条没有单号的待人工**。所以认领响应带 `claim_timeout_min`（取自
`registry.settings.claim_timeout_minutes()`），插件永远给服务端留出余量。

**这本账从「认领」那一刻起算,不是从「点了下单」那一刻。** `flow/run.ts` 在
`runTask` 入口就把 `认领时刻 + claim_timeout_min×60s` 这个**绝对时刻**记下来,
再交给 `placeOrder`。少了这一步的话,清车(上界 350s)、加购、`checkoutNav`(45s)、
地址(60s)那几步花掉的五六分钟不进任何一本账 —— 而它们同样记在服务端的
`claimed_at` 上,于是插件算出来的「还能等多久」一直是偏大的,默认配置下
(15 分钟认领超时、10 分钟 `orderHardCap`)总时长能到 16 分钟,越过清扫线。

**到期的码分两种，因为现场是两种。** 停在验证页上到期是
`PAYMENT_VERIFICATION_TIMEOUT`（订单多半已经提交），其余两段是
`ORDER_CONFIRM_TIMEOUT`（常见成因是根本没点动那个按钮）。两者同属
`TO_MANUAL` + `POSSIBLY_ORDERED`。

**为什么不学厂商「一直等下去」。** 不是保守：在我们的架构里那个等待**等不到任何人**。
所有 iframe 挂在一个 `left:-10000px; pointer-events:none` 的宿主上，
不 `reveal()` 就是等一个永远不会来的事件；而 `busy` 闸不复位的话，这个标签页
从此安静地什么都不干，服务端 15 分钟后把这条判成 `CLAIM_TIMEOUT` ——
与厂商 `purchaseBatchInProgress` 永不复位是同一个形状，只是我们的锁叫 `busy`。
**放弃的方式是让上界到期，不是给操作员一个能让 Promise 永挂的关闭按钮。**

插件侧还有一道最后的兜底:`Loop.tickOnce` 用 `Promise.race` 给整单套一个硬顶,
到点强制 `driver.dispose()`、上报一条 step、并挡住下一次认领直到那条 runTask
真的落地 —— 每一步自己都有上界,所以正常情况下永远轮不到它;它防的是那件
我们没想到的事。这个硬顶取 `cfg.taskHardCapMs`(默认 20 分钟)与
`claim_timeout_min×60s − 余量` 里更紧的那个:不钳的话,20 分钟比默认 15 分钟的
认领超时还长,看门狗触发时任务在服务端**必然已经不是 claimed 了**,
它那条「插件放弃这一单」的 step 会被 `TASK_NOT_HELD` 拒掉 ——
事件流里再没有任何地方说过是插件先放弃的。那条日志也不再写死
「任务在服务端仍是拍单中」,而是按此刻的钟说话。

被掐掉的那条 runTask 在真正落地之前会挡住下一次认领(相位 `stuck`,
**插件面板上说得出名字** —— 不是灰色的「待命」),**而这一等也有界**:
再等一个 `taskHardCapMs` 还没落地就不等了,并且说清楚不等的后果
(它稍后真走完的话,收尾清车会和新领的一单撞在同一个购物车上)。
`dispose` 未必解得开我们没想到的那种挂起,而「所有等待都必须有界」
这条对它同样成立。

**运营台上这一格现在是空的 —— 记在这里,别让它悄悄变成一句假话。**
心跳只上报 `login_state`(`server/schemas.HeartbeatReq`),没有任何一列知道
这台机器此刻处在 `stuck` 还是 `cart-blocked`。于是:清车熔断暂停认领的那 10 分钟
(`cartBlockMs`)、看门狗掐单后最长一个 `taskHardCapMs` 不认领的那 20 分钟,
心跳照常打,`services/instance.list_with_liveness` 算出的 `dispatchable` 仍是 true,
买家号页显示「在线 · 可派」,而队列一动不动 —— 正是这一页存在的理由
(登录态那一列的原话:「被登出的买家号在这一页上是满格绿色的『在线 · 可派』」)。
`cart_fail_24h` 那一列是个**近似替身**:它数的是导致熔断的失败,不是熔断本身,
而且只覆盖 24 小时;`stuck` 连替身都没有。
补它的形状是明确的:心跳带上一个封闭集的 `runner_phase`
(`idle` / `cart-blocked` / `stuck` / `busy`),买家号页多一列并进 `dispatchable`
的说明。**没做**,因为它要动表(`plugin_instances` 加一列)、动心跳契约、
动那一页的判据 —— 是一件独立的事,不该顺手塞进一轮修复里。
在它落地之前,一台停摆的机器只有插件面板上说得出。

## 9. 分阶段实施

| 阶段 | 交付 | 验收 |
|---|---|---|
| **P0** | `registry` + `refdata/schema.sql` + `cli.py db_init` + `services/task_queue` | 建库成功；两个实例并发认领同一环境，只有一个拿到任务 |
| **P1** | `server/` 全部端点 + mock 插件脚本 | 不碰 Amazon，跑通 认领→上报→完成/失败→状态流转 |
| **P2** | 插件骨架：注册、心跳、认领、上报；执行流留空 | 真插件跑通 P1 的全链路 |
| **P3** | 拍单主流程：加购→结算→填址→下单→单号 diff 回填 | 测试账号完成一次真实小额下单并正确回填 |
| **P4** | 护栏全覆盖 + 运营台接口 + `task_sweep` | 构造超限价/超期/缺货用例，均被拦截并转人工。`erp_sync` 换成了 `task_intake`：上游真实接口未接，先走文件投放，形状与将来的接口一致 |
| **P5** | 物流同步 + 后台查询接口 | 轨迹入库，错误码分布可查 |

P0/P1 完全不碰 Amazon，风险最低，先跑通。

## 附录 B：安全与合规（暂缓，记录在案）

所有者决定先把项目做出来，以下项不进首期，但设计上已预留不返工的余地：

| 项 | 现状 | 备注 |
|---|---|---|
| 鉴权 | 不做 | 服务只在内网监听。将来要加，只需在 `server/app.py` 挂一个依赖，不动 services |

| 反检测 | 不做 | 命中风控 → `CAPTCHA_ENCOUNTERED` → 转人工 |
| 第三方 CDN | 不引入 | 静态资源走 `web_accessible_resources` 内置 |

> 自动化下单与 Amazon 使用条款存在冲突，账号风险由账号持有方承担。本设计做到「可控、可审计、出问题能停」，不承诺规避平台规则。
