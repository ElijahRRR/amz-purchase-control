# web/ —— 运营台前端

Vite + React 18 + TypeScript / TanStack Table + Virtual / Tailwind + 自建 shadcn 风格组件 / Recharts。

```bash
npm install
npm run dev        # → http://127.0.0.1:5173,/v1 由 Vite 代到 8781
npm run build      # → dist/,由 server/app.py 挂在 / 上
npx tsc -b         # 只做类型检查
```

四页:**任务队列**(主界面)/ **买家号** / **工作流记录** / **错误码分布**。

## 写进代码的几条规矩

**封闭集不存副本。** 状态、物流状态、事件类型、错误码及其四个处置分组,
全部由 `GET /v1/admin/meta` 下发。这个项目已经因为「两份副本悄悄分叉」栽过两次
(厂商的 `subTotal`/`subtotal`、我们自己的 docs 目录树)。
想加一个状态,改 `services/vocab.py` 一处就够。

界面上出现一个陌生的英文枚举是**对的** —— 那说明服务端加了新值而前端还没发版。
静默映射成「未知」会让人以为库里真有个叫「未知」的状态。

**词汇表缺键就不渲染,并且说出缺了哪个。** 前后端分开发布,版本一错位就会对
`undefined` 调 `.includes`,整站白屏。白屏跟「服务挂了」「网断了」长得一模一样,
运营会去重启一台其实好好的机器。所以 `MetaGate` 校验形状,缺了就明说缺哪个键。

**「可派单」这种结论一律由服务端算,前端只显示。** 买家号那一页的「可派/不可派」
与认领那道真闸(`services/task_queue`)算的必须是同一件事 —— 这里分叉过一次:
「可派单」曾只看在线、不看 `daily_cap`,于是拍满配额的机器在界面上仍然是绿色可派,
而界面里那个「已到日上限」的分支永远走不到。登录态这一项同理:
前端拿的是服务端算好的 `login_blocks_dispatch`,**不自己判**
`login_state === "signed_out"`。

**同一列里两种不同的情况不许长成一个样子。** 买家号那一页的「登录态」写的是
「已登录 / 已登出 / 登录态存疑」三个词,旁边还带上次检查的时刻 ——
「读不到导航栏」和「读到了、登录着」是两件事,渲染成同一个绿标签就等于那道闸没有;
一分钟前读到的「已登录」和三天前读到的也不是一回事。

**「不适用」不是「未超」,也不是「未核」。** 外部下单的单(上游自己在别处买的,
本系统只同步物流)没走过我们的结算页,`price_cap` 是库里那个 NOT NULL 的占位 0。
拿它去比会得出「0 ≥ 0,未超」——**一句护栏从没做过的结论,还配一个绿点**。
所以列表/详情/CSV 对它一律写「外部下单,不适用」;而「未核」留给
「本该核、这次没核成」(金额没回传、读成了 0),看到它的人会去查。
判据只有一处:`lib/utils.capVerdict`(服务端那半在 `services/task_query.over_cap`)。
这一格已经栽过两次(null、"0.00"),这是第三种形状。

**「一律」包括紧凑档。** 紧凑档一度是唯一还在把那个占位 0 渲染成「限价 0.00」的地方
(详细档与 CSV 都写对了),而**扫桶用的正是紧凑档**;同一格的颜色也是自己写的
三分支,新加的第四档落进 else,与一张真核过、没超的单拿到同一个 class。
现在颜色直接取 `capVerdict().tone`,查表的键写成 tone 的全集 ——
再加一档而忘了给颜色,`npm run build` 当场报错,不会安静地落进某个 else。
⚠ 运营台这一侧**没有测试**(全仓没有 web 测试运行器),这一条只有类型检查盯着。

**「登录态」与「买家号ID」是两条独立的轴。** 前者答「还登着吗」,后者答
「登着的是不是**这个号**」。心跳一秒不落、登录态「已登录」的机器,
浏览器里登的完全可能是隔壁那个号 —— 派给它一单,它会用另一个买家号真买下来。
「以这个为准」那个按钮**会打开一道认领闸**,所以它过一次确认,
服务端还会带着操作人写进 `procure.env_events`。

**「没说上话」和「服务说不行」是两句话。** `ApiResult` 分 `transport` / `business`,
调用方必须分别处理 —— 界面上「查不到」和「服务挂了」混成一句,
会让人跑去上游翻一张其实好好的单。

**复制失败要出声。** `navigator.clipboard` 只在安全上下文可用。静默失败在这里特别毒:
运营以为地址已经复制,粘到亚马逊的却是上一次的剪贴板内容,包裹直接寄错人。
所以 `CopyText` 失败会变红说「复制失败」,并且有 `execCommand` 兜底。

**红色要跟真正那道闸算的是同一件事。** 限价是**整单**的,而那道闸判的是
`goods_total > price_cap` —— **货款 = 实付 + 礼品卡抵扣**,不是这张卡扣了多少。
所以红色标在「货款」那一行上(有礼品卡时详情里会多出这一行),
「实付总计」在有礼品卡的单上**刻意不着色**:它不是被比过的那个数。
拿单价去比会得出跟护栏相反的结论:3 件 × 24、限价 60,单价看着安全、整单其实已经超了;
拿实付去比更糟 —— 礼品卡全额抵扣的单实付 0.00,画绿点写「未超」,而货款可能超了一倍。

**危险动作前端不替人做决定。** 重置一律先按 `acknowledged: false` 发,
让服务端那道 `NEEDS_ACK` 闸自己判;它拒了再弹确认条给人回应。
由前端看错误码自动带上 `acknowledged`,等于把闸拆了 ——
而闸上写着的正是「这一单可能已经真下成了」。

**必然被拒的按钮不该亮着。** 已下单/已取消的单点「改地址」服务端会以 `BAD_STATUS` 拒,
所以那两个按钮在这些状态下不渲染。一个点下去必然被拒的按钮,
是在让人以为自己做错了什么。

**只发真改动过的字段。** 地址表单原样回传六个字段的话,事件流里那条 `before`/`after`
会记成「六个字段全改了」,以后查「谁把州改错了」就查不出来了。

**别在界面上撒谎,而「实话」是跟着配置变的。** `RETRYABLE` 那一组现在有
`workflows/task_retry.py` 在消费,但它**默认关着**(`AMZ_AUTO_RETRY_MAX=0`)。
所以关于这一组的每一句话都从 `meta.auto_retry` 来,不写死:
关着说「需人工重置」,开着说「系统最多自动重试 N 次(已试 k 次)」。
两个方向都会害人 —— 关着却说会自动重试,一桶没人管的单被晾着;
开着却说要人工重置,人会去点已经排队等系统重的单。
详情弹窗还会显示这一单**被机器**重过几次(人点的重置不计数)。

而「跟着配置走」还只是一半:**还得跟着这一单自己的状态走**。「上限 N 次」是一句
承诺,只对真排着队等机器重的那种单成立 —— 一张 `status=manual` 却带着 RETRYABLE
码的单(插件越过下单点后抛 DriverError 就会落成这样),机器永远不会碰它,要人
**现在**去订单页看。这两种单要是渲染出同一句「已试 0 / 上限 2」,运营就会照着
「重满了才要人管」把它晾着。所以凡是写「上限」「不点它也会被放回队列」的地方,
都得先过一遍 status、错误码分组和那道年龄闸(`meta.auto_retry.max_age_min`)。

**一张永远红着的卡片会把人训练成忽略红色。** 工作流记录页只把「该定时却太久没跑」
标红;`db_init` 这种装机时跑一次的按需工作流标灰。
期望写在 `services/ops_query.EXPECTED_INTERVAL`,加了工作流却没声明的测试会断。

**折线图上「平了」和「没数据」长得一样,含义正好相反。** 所以按天的趋势图会把
没出错的那天补成 0,并且用 `linear` 而不是 `monotone`——
后者会在两天之间画出从没存在过的峰值。

**批量动作不替人做那个必须由人做的确认。** 批量重置调的是一个**没有 `acknowledged`
参数**的接口。能重的都重,可能已下单的原样报回来,界面把它们单独列成一行紫字,
说清楚「点开逐条去买家号的订单页看过再重置」。「跳过」不是失败 ——
混进失败里会让人以为系统出了问题,于是重试,于是绕过那道闸。

勾选框只在拍单异常 / 待人工的行上可用:让必然被拒的单能被勾上,
只会换来一份「失败 18 条」的清单。换了筛选或翻了页就清空勾选 ——
留着的话,「重置选中的 12 条」会包含现在根本看不见的单。

**导出的是整个筛选结果,不是当前这一页。** 只导一页是最阴的那种错:
表看着完整、其实少了后面几千行,而且没有任何地方提示少了。

**一单多商品会展开成多行,整单金额逐行重复 —— 别对这几列求和。**
一张 3 个 ASIN 的单在 CSV 里是 3 行,「实付总计」「礼品卡抵扣」「货款」「运费」
「税费」「整单限价」每行都带整单值(表格软件里按 ASIN 筛的人要的就是这个)。
在 Excel 里对这几列求和会把金额乘以商品行数。逐行不同的只有
「ASIN」「数量」「实付单价」那三列。

**CSV 里有一列「来源」(插件下单 / 外部下单 / 人工回填),对账时先按它分开看。**
外部下单那一批的费用几列**本来就是空的**(那单不经本系统采购),
不知道来源的人会把它当成「同步掉了」;而「人工回填」那一批是**回填时那道 ASIN
断言被跳过的**,回头查「有没有挂错单号」要先看它们。

**「操作人」不是登录。** 自己填的名字,存浏览器本地,由 api 层统一带上。
这套东西不做鉴权(所有者定稿),没有可信身份可用 ——
它只是让人工动作在事件流里带上一个人名,拦不住任何人。界面上写明了这一点。

## 两种行密度

- **详细**(~124px):照厂商面板那一行做,8 组字段竖着堆在各自格子里
  (所有者定稿:「这是订单详情,需要把它作为模板」)。运营不用点开就能核对
  地址、费用、物流 —— 这正是他们现在的工作方式。
  **顺序上只改了一处**:「其他信息」(状态标 + 错误码标 + 「等人工验证」徽标 +
  「已越过下单点」)从最后一格挪到了最前面。它原先排在最右,而 1440 / 1512 / 1680
  这些常见笔记本宽度下前面几组已经把内容区吃满,那一列被压到 24px、
  默认滚动位置下整列在屏幕外 —— 一个「有人正在等你」的徽标在默认档上看不见。
  窄屏时被挤到屏幕外的换成了「买家号信息」。
- **紧凑**(40px):一行一条,用来扫桶:今天异常几单、卡在哪。
  「实付」那一格在有礼品卡抵扣时显示的是**货款**(带一个极小的「货」角标)——
  红色必须落在它标注的那个数上,否则屏幕上会出现「限价 1200.00 / 实付 1141.86(红)」
  这种两个数字说没超、颜色说超了的一行。

**窄屏时让位的那一列是标了 `meta.flex` 的那一格**(收货 / 买家信息),不是「最后一列」。
让最后一列去吃 `1fr` 的写法有个坏毛病:内容区不够宽时它被压到只剩内边距,
表格又不横向滚动,人没有任何提示说右边还有东西。让位的必须是**截断了也不丢信息**的格子。

表格用 `display: grid` 而不是默认的 table 布局 —— 虚拟滚动要给行绝对定位,
原生 table 的行排不动。

## 订单详情

**点行才弹**,不默认占着右边一栏(所有者定稿)。布局照厂商面板那一行的
8 组字段与顺序,分组名也沿用他们的说法 —— 运营从那边迁过来时,
眼睛不用重新学一遍东西放在哪。

与厂商那边有两处刻意的不同:

- 他们整段执行过程只有一个 `failContent` 自由文本字段;我们换成只追加的事件时间线。
- 危险动作(强制回填)必须先过一个**预览步**,把「要写进库的到底是什么」摊开说清楚。

## 点击即复制

ASIN、上游单号、AMZ 单号、收货各字段、运单号、买家号 ID,外加收货地址「复制整段」。
规则挂在 `CopyText` 上,不是一个字段一个字段挂事件。复制不冒泡 ——
行本身是可点的(点行开详情),复制不该顺手把弹窗也开了。
