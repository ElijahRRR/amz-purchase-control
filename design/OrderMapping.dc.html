订单详情字段映射 厂商面板那一行 8 组字段 → 我们库里的落点 来源:vendor-panel-analysis §2.3(38 字段行模型) · 插件功能深度分析 §5.1 / §5.2(两个回传体)
厂商那一行 店铺信息 买家信息 产品信息 订单信息 费用信息 物流信息 买家号信息 其他信息
店铺信息 3 个字段
storeName→不存店铺留在上游 ERP,采购侧不需要知道是哪家店
orderNo→tasks.line_key = sha256(上游单号|asin) · 他们是把两截字符串直接拼起来当主键,人眼分不出边界(截图里 119122366387352 + B0F834Q858 连在一起)
country→tasks.marketplace · 首期恒为 US
买家信息 上游下发,只读
receivingName→tasks.ship_name
receivingPhone→tasks.ship_phone
receivingAddress→tasks.ship_line1
receivingCity / State→tasks.ship_city / ship_state
receivingPostCode→tasks.ship_postcode
receivingCountry→tasks.ship_country
receivingDistrict→不做日本站才必填,首期只有 US
platformPostCode→不存影子字段,专门用来跟导入值比对 · 我们的地址是自己填进去的,没有第二份可比
产品信息 支持多商品行
imgUrl→task_products.image_url · 列表里 ASIN 左边那张图
asin→task_products.asin
quantity→task_products.quantity
price→换了语义tasks.price_cap —— 他们这是导入价,只摆着看;我们是限价,超了不采
(他们没有)→task_products.actual_unit_price · 结算页实测单价,回传时填
订单信息 回填与校验
platformOrderNo→tasks.amazon_order_no · 加了部分唯一索引:同一个 AMZ 单号不可能落到两条任务上
asinCheck ✓/✗→不存不存两份再打叉,而是回填那一刻断言,不符直接不写(ORDER_NO_AMBIGUOUS)
postCodeCheck ✓/✗→不存同上
费用信息 来自 purchaseOrderFinishUpdate(§5.1)
shipping→tasks.actual_shipping
tax→tasks.actual_tax
total→tasks.actual_total · 护栏拿它跟 price_cap 比
totalBeforeTax→不存展示时算:actual_total − actual_tax
subTotal→不存他们这一列恒为空:插件里 subtotal 声明后从未赋值,而且回传的 key 是小写、面板读的是驼峰 · 我们用 actual_unit_price × quantity 自己算
物流信息 来自 updateTrackingInfo(§5.2,20 字段)
platformTrackCarrier→shipments.carrier · 他们这个值是页面文本 split(" ")[2] 盲取第 3 个词,截图里就是 --
platformTrackNo→shipments.tracking_no
orderStatus→shipments.status · 未发货 / 运输中 / 已签收 / 已取消(库值 not_shipped / in_transit / delivered / cancelled)。他们的「未同步 (0)」在我们这儿不是枚举值,是这行还不存在
deliveryTime→tasks.delivery_date
origDeliveryTime→tasks.delivery_raw · Amazon 原文,解析失败时的唯一线索,必须留着
events[]→logistics.shipment_events · day / time / 描述 / city / state,seq 0 最新
deliveryTimeAbnormal→换了做法他们是黄字提示、无系统动作;我们用 max_delivery_days 在下单前硬拦(DELIVERY_TOO_LATE)
trackingHtml→不存整页 HTML + 内联全部 CSS 的 base64,无长度上限 · 我们只存结构化事件
买家号信息
buyerAccount→buyer_envs.code · 值其实是防关联浏览器的环境名
buyerCustomerId→buyer_envs.amazon_customer_id
paymentCard→tasks.payment_last4 · 列必须是 text:插件在识别到「用积分付」时会把这个字段直接写成中文「礼品卡」,按纯数字建表会炸
同步时间→没这概念那是「等插件回传」的等待态 · 我们用 plugin_instances.last_seen_at + task_events
其他信息
status→tasks.status · 他们 4 个,我们 7 个。界面上沿用他们的说法(待拍单 / 已拍单 / 拍单异常),多出的两个自己起名:拍单中、待人工。英文只在库和 API 里,界面不出现 —— 完整对照见设计系统板
failContent→换了做法error_code + error_detail + task_events 全流 · 一个自由文本字段换成 19 个封闭错误码加只追加的事件流
createTime→tasks.created_at
purchaseTime→tasks.purchased_at
remark→不做那是 Excel 导入的批次备注,我们没有导入通道
createName→不做单子由上游下发,不是人在这里建的;而且本系统不做鉴权,没有用户
截图里的算术:导入价 ≠ 实付价
产品信息写着 价格 13.99 · 数量 3,按说税前该是 41.97,可费用信息里税前总额是 $37.77 —— 实付单价其实是 12.59。导入价和实付价是两个东西,他们并排摆着却从不比较。 我们把这个位置换成上游算好的限价,并且在下单前拿实付跟它比。
在途不该是红色
截图里物流状态「运输中」是个红标签。红色一旦用来表示正常在途,真出事时就没有颜色可用了。 我们的在途是天蓝虚线 运输中,红色只留给「坏了」。
一行装不下,才要弹详情
8 组字段全塞进一行,结果是横向拖着看,而且没有一处能放事件流。我们把决策需要的留在列表里, 其余 8 组按同样的分组与顺序放进点击才弹出的详情,末尾补上他们没有的事件时间线。
